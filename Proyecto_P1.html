De la teoría a la práctica: walkthrough en acción

Auditoría de seguridad sobre la máquina vulnerable DigitalWorld.local: SNAKEOIL (VulnHub)

ACTIVIDAD
PR
ALUMNO
Aaron Emanuel González Díaz (182447)

1. Objetivo de la Actividad

Demostrar la capacidad de aplicar conocimientos teóricos de seguridad informática en un entorno práctico, mediante la realización de un walkthrough detallado sobre una máquina virtual intencionalmente vulnerable, explicando las técnicas y metodologías utilizadas para comprometer el sistema objetivo.

2. Descripción del Escenario

La práctica consistió en auditar "DigitalWorld.local: SNAKEOIL", una máquina de Debian 10 que aloja una aplicación web desarrollada en Flask con autenticación basada en JSON Web Tokens (JWT), simulando el desarrollo interno de la empresa ficticia "Good Tech Inc." El objetivo fue identificar y explotar las fallas de seguridad introducidas deliberadamente en su código.

3. Configuración del Laboratorio

  • Sistema Operativo Atacante: Kali Linux (VirtualBox)
  • Dirección IP del Atacante: 192.168.56.101 (interfaz eth0, red solo-anfitrión)
  • Dirección IP del Objetivo: 192.168.56.102
  • Herramientas Utilizadas: nmap, gobuster, Burp Suite, John the Ripper, netcat
  • Servicios Objetivo: SSH (22), nginx (80 y 8080 — aplicación Flask con API JWT)

4. Resumen de Funcionamiento y Evidencias

4.1 Reconocimiento y Enumeración

Se identificó la IP objetivo mediante netdiscover y se escanearon sus puertos con nmap -sV. Con gobuster se descubrieron los endpoints de la API: login, users, registration, run, secret y test.

4.2 Control de Acceso Roto Confirmado

El endpoint /registration permitió crear cuentas de usuario sin ninguna restricción, obteniendo un token JWT válido de forma inmediata.

4.3 Exposición de Clave Secreta Confirmado

El endpoint /secret devolvía error 500 al enviarse el token como cabecera Authorization. Al enviarlo como cookie access_token_cookie, el servidor reveló la clave requerida por /run:

{"secret_key": "commandexecutionissecret"}

4.4 Inyección de Comandos del Sistema Operativo Confirmado

El parámetro url del endpoint /run se concatenaba sin sanitizar dentro de un comando curl en el servidor, permitiendo ejecución arbitraria de comandos:

POST /run {"url":"192.168.56.102:22;<comando>","secret":"commandexecutionissecret"}

4.5 Obtención de Shell Remota Confirmado

Un primer intento de reverse shell en Bash fue bloqueado por un filtro de palabras ("Banned Command"). Se evadió codificando el payload en Base64 y, alternativamente, usando una reverse shell en Python, logrando una conexión interactiva hacia un listener de netcat.

4.6 Credenciales en Código Fuente Confirmado

Dentro del sistema comprometido se localizó el archivo de configuración de Flask con las claves embebidas en texto plano:

SECRET_KEY = "snakeoilisnotgoodforcorporations" JWT_SECRET_KEY = "NOreasonableDOUBTthisPASSWORDisGOOD"

4.7 Escalación de Privilegios a Root Pendiente

No se completó la escalación al usuario root del sistema operativo dentro del tiempo disponible para la actividad; queda documentado como trabajo futuro.

5. Flujo de Explotación

  1. Reconocimiento: escaneo de red y de puertos para identificar servicios expuestos.
  2. Enumeración: descubrimiento de endpoints ocultos de la API con gobuster.
  3. Registro y autenticación: creación de una cuenta arbitraria mediante /registration.
  4. Extracción de la clave secreta: uso correcto del mecanismo de cookies JWT en /secret.
  5. Explotación de la inyección de comandos: ejecución de comandos arbitrarios vía /run.
  6. Post-explotación: obtención de shell remota y descubrimiento de credenciales adicionales en el código fuente.

6. Controles de Seguridad Propuestos

  • Control de acceso y autorización: restringir y validar todos los endpoints de la API, incluyendo registro y edición de contenido.
  • Gestión de secretos: usar variables de entorno o gestores de secretos en vez de embeber claves en el código fuente.
  • Validación de entradas: sanear y validar estrictamente cualquier parámetro que se use en llamadas al sistema operativo, evitando la concatenación directa de comandos.
  • Principio de menor privilegio: ejecutar los servicios de la aplicación con el mínimo de permisos necesarios para limitar el impacto ante una posible explotación.

7. Conclusión

Esta actividad permitió encadenar múltiples vulnerabilidades —control de acceso roto, mala configuración de JWT, exposición de secretos e inyección de comandos— para comprometer completamente el sistema objetivo, evidenciando cómo fallas aparentemente menores pueden escalar hasta comprometer un servidor por completo cuando no se aplican buenas prácticas de desarrollo seguro.
